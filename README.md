# Quick-commerce stockout platform

A data-engineering project built on Azure Databricks: find which dark-store shelves run empty, estimate the sales lost, and rank what to restock.

> **Data note:** orders and shelf stock are **synthetic** (generated by `data_generator/`), because quick-commerce companies do not publish theirs. Weather is **real** hourly data from Open-Meteo. Every rupee figure is an estimate on simulated data.

## The problem
Dark stores serve ~10-minute delivery from small shelves. When a product runs out the sale is lost; when too much is held, fresh stock is wasted. Demand moves with the hour, the weekday and the weather, so nobody can track it by hand across stores and products.

## What the pipeline does
1. Ingests hourly order, shelf-stock and weather files incrementally (Auto Loader).
2. Cleans them: deduplicates, validates, and quarantines rejected rows with a reason.
3. Builds a star schema (one fact row per store, product and hour: 115,200 rows).
4. Finds stockout spells, learns a demand model and the weather effects, and estimates lost sales.
5. Ranks the shelves most at risk of running out before the next restock.
6. Checks itself with 38 automated data-quality checks and fails loudly if any error-level check fails.

## Architecture

    laptop: generate synthetic orders/inventory + download real weather
        |  upload
        v
    ADLS Gen2   landing/
        |  Auto Loader (incremental, idempotent)
        v
    bronze/   raw Delta tables + audit columns (_source_file, _ingested_at)
        |  dedupe, validate, quarantine, MERGE upserts
        v
    silver/   clean Delta  +  _quarantine/ (rejected rows)  +  _run_log
        |  star schema, stockout spells, demand model, weather effects
        v
    gold/     dimensions, fact table, marts, ops_dq_results

    Orchestration : Databricks Workflow, 6 chained tasks, hourly schedule, email on failure
    Quality gate  : last task runs 38 checks and fails the run on any error-level failure
    Monitoring    : Azure Monitor log alert on failed Databricks job runs
    Security      : managed identity for storage access (no keys), Key Vault-backed secret scope (demo)
    CI            : GitHub Actions - ruff, pytest, Bicep build

## Results (September 2026: 10 stores, 16 products, 720 hours)
| Measure | Result |
|---|---|
| Orders | 168,147 raw rows, 1,665 duplicates removed, 166,482 clean |
| Shelf readings | 115,200 received, 230 invalid (negative) quarantined |
| Share of observed store-product-hours with an empty shelf | 23.6% |
| Stockout spells | 2,974 (average 9.1 hours, longest 20 hours) |
| Estimated sales lost to stockouts | about Rs 1.05 million against Rs 8.2 million actually sold |
| Lost-sales estimate vs the generator's hidden truth | 94.2% of true lost units, correlation 0.991 across store-products |
| Weather correction | rainy hours 71.6% to 92.2% of truth; hot hours 85.4% to 98.8% |
| Weather effects found from sales alone | e.g. chips 1.50 (true 1.5), coffee 1.40 (true 1.4), cola 1.32 (true 1.4), ice cream 1.51 (true 1.6) |
| Restock-list backtest, 22-29 Sep | precision 85.8%, recall 86.0%, run-out timing error 1.1 to 2.0 hours per day |

## Data quality and operations
- 38 checks across reconciliation, Silver, Gold, completeness and model guards. A self-test injects defects (duplicate, bad quantity, null store, unknown store) and confirms each is caught.
- The workflow ran about 14 times (manual and hourly); every task succeeded in every run, typically 12 to 22 minutes including cluster start.
- A deliberate failing run was used to prove both alerts: the Databricks failure email (within about a minute) and the Azure Monitor log alert (about nine minutes later).
- 10 unit tests (data-quality detectors, stockout-spell logic, secret-scanning check) run in CI on every push.

## Known limitations
- Orders and inventory are synthetic. The "true lost sales" check is only possible because the generator records them; real companies cannot do this.
- The restock backtest is in-sample and uses the actual weather as the forecast.
- The Silver MERGE rewrites every row on each hourly run (the dataset is static, so no new files arrive). A condition to update only changed rows is the obvious fix.
- The demand "level" is estimated from hours that still had stock, which likely biases it slightly low (an untested hypothesis).
- The Key Vault secret is a demonstration; the pipeline's real access uses a managed identity.
- Bicep covers Azure resources only, not Databricks objects such as the job or external locations.
- Built on an Azure free account; the cloud resources are removed when the credit period ends, so what remains is code, exported results and screenshots.

## Reproducing it
1. `pip install -r requirements.txt`
2. `python data_generator/generate_data.py`, then `python data_generator/fetch_weather.py`
3. Upload `data/raw` and `data/truth` to a `landing` container in ADLS Gen2.
4. Import the notebooks and run `01` to `06` in order, or chain them as a Workflow.
